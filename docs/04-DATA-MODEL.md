# 04 - Data Model (PostgreSQL 17)

The complete schema of SmartSilk (Nexora), as table specifications. It is the single reference for every Flyway
migration. Migrations V1-V5 already exist and are reproduced exactly; V6 onwards are specified here.

Precedence when documents disagree: `DOMAIN_RULES.md` and `DECISIONS.md` first, then `CONVENTIONS.md`, then this file,
then the design notes in `smart-ledger-docs/`. Section 18 lists every place where this file chose between sources.

---

## 1. Global conventions

| Topic | Rule |
|---|---|
| Names | `snake_case`; plural table names; FK columns `<entity>_id` |
| Primary key | `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` (unnamed PK, as in V3-V5). Pure junction tables use a composite PK named `pk_<table>` |
| Business numbers | `VARCHAR(30)` + `uq_<table>_<col>`; generated by `BusinessNumberGenerator` as `PREFIX-YYYY-NNNN` |
| Money | `NUMERIC(14,2)`; weight in kg `NUMERIC(12,3)`; hours `NUMERIC(8,2)`; percent `NUMERIC(6,3)` |
| Dates | business date `DATE`; system timestamp `TIMESTAMPTZ` (UTC) |
| Enums | `VARCHAR(n)` + a named `CHECK (col IN (...))`; never PostgreSQL ENUM types |
| Constraint names | `pk_`, `fk_<table>_<ref>`, `uq_<table>_<cols>`, `ck_<table>_<rule>`, `ix_<table>_<cols>` |
| Foreign keys | `ON DELETE NO ACTION` (the PostgreSQL default, equivalent to RESTRICT here). No cascades anywhere: nothing is ever physically deleted |
| FK indexes | Every FK column has an index (PostgreSQL does not create them) |
| NULL | Only for "not known yet / not applicable". No fake values |
| Deletes | No hard deletes of business data. Master data uses a status; documents use a status or reversal |
| Derived values | Never stored (DOMAIN_RULES section 6). The only projection is `inventory_balances` |

### 1.1 STD columns (standard audit block)

Every table below marked **+STD** carries these five columns. The Java base class `AuditableEntity` maps them.
`updated_at` and `version` are maintained by JPA; no DB trigger sets them.

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `created_at` | TIMESTAMPTZ | NOT NULL | `now()` | filled by JPA auditing |
| `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | filled by JPA auditing |
| `created_by` | UUID | NULL | - | the acting user from the JWT; NULL for system actions. `fk_<table>_created_by` -> `users(id)`, index `ix_<table>_created_by` |
| `version` | BIGINT | NOT NULL | `0` | optimistic lock (`@Version`) |

Append-only tables (section 14) also carry STD so the single base class works; their `updated_at` and `version` never
change after insert (a trigger forbids UPDATE).

## 4. Inventory (migration V6)

### 4.1 `inventory_balances` (+STD) - the projection and the lock anchor

Current stock per (product, location). A **projection** of `material_movements`, updated in the same transaction as each
movement and rebuildable from them (`quantity_kg = Σ in − Σ out`). The row is the pessimistic-lock anchor.

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `id` | UUID | NOT NULL | `gen_random_uuid()` | PK |
| `product_type` | VARCHAR(20) | NOT NULL | - | ProductType |
| `location` | VARCHAR(20) | NOT NULL | - | internal locations only |
| `quantity_kg` | NUMERIC(12,3) | NOT NULL | `0` | |
| STD | | | | |

- `uq_inventory_balances_product_location UNIQUE (product_type, location)`
- `ck_inventory_balances_product CHECK (product_type IN ('RAW_SILK','SILK_WARP','KORA_WARP','VUDA_WARP'))`
- `ck_inventory_balances_location CHECK (location IN ('RAW_STOCK','INTERNAL_WIP','EXTERNAL_WIP','FINISHED_STOCK'))`
- `ck_inventory_balances_quantity CHECK (quantity_kg >= 0)` - stock can never go negative (last line of defence)
- `ck_inventory_balances_location_product CHECK ((location='RAW_STOCK' AND product_type IN ('RAW_SILK','VUDA_WARP')) OR (location IN ('INTERNAL_WIP','EXTERNAL_WIP','FINISHED_STOCK') AND product_type IN ('SILK_WARP','KORA_WARP')))`
- Rows are created on first use (`INSERT ... ON CONFLICT DO NOTHING`, then `SELECT ... FOR UPDATE`). No seed rows.

### 4.2 `material_movements` (+STD) - the inventory ledger (append-only)

Every stock change is exactly one row. Quantities are positive; direction comes from `from_location` -> `to_location`.

Because raw silk becomes warp inside work-in-progress, a movement carries two product types: `product_type` is what
leaves `from_location`, `to_product_type` is what arrives at `to_location`. They differ only for `CONSUMPTION` and
`OUTSOURCE_ISSUE` (raw silk goes in, the target warp type is recorded as work in progress). Work in progress is therefore
tracked by the warp type being made.

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `id` | UUID | NOT NULL | `gen_random_uuid()` | PK |
| `movement_number` | VARCHAR(30) | NOT NULL | - | `MOV-2026-0001` |
| `product_type` | VARCHAR(20) | NOT NULL | - | product leaving `from_location` |
| `to_product_type` | VARCHAR(20) | NOT NULL | - | product arriving at `to_location` |
| `movement_type` | VARCHAR(30) | NOT NULL | - | MovementType |
| `quantity_kg` | NUMERIC(12,3) | NOT NULL | - | > 0 |
| `from_location` | VARCHAR(20) | NULL | - | NULL only for `OPENING_BALANCE` |
| `to_location` | VARCHAR(20) | NOT NULL | - | |
| `movement_date` | DATE | NOT NULL | - | business date |
| `reference_type` | VARCHAR(30) | NULL | - | polymorphic source |
| `reference_id` | UUID | NULL | - | no FK (polymorphic) |
| `reason` | VARCHAR(255) | NULL | - | required for `ADJUSTMENT`; used for `WASTAGE` sub-reason |
| `notes` | TEXT | NULL | - | |
| STD | | | | |

Constraints:
- `uq_material_movements_movement_number UNIQUE (movement_number)`
- `ck_material_movements_product CHECK (product_type IN (4 values) AND to_product_type IN (4 values))`
- `ck_material_movements_movement_type CHECK (movement_type IN (12 values))`
- `ck_material_movements_quantity CHECK (quantity_kg > 0)`
- `ck_material_movements_locations CHECK ((from_location IS NULL OR from_location IN (8 values)) AND to_location IN (8 values) AND (from_location IS NULL OR from_location <> to_location))`
- `ck_material_movements_type_locations` - the (type, from, to) table of DOMAIN_RULES section 3:

| movement_type | from_location | to_location |
|---|---|---|
| `OPENING_BALANCE` | NULL | `RAW_STOCK`, `INTERNAL_WIP`, `EXTERNAL_WIP`, `FINISHED_STOCK` |
| `RECEIPT` | `SUPPLIER` | `RAW_STOCK` (raw silk and vuda warp) |
| `PURCHASE_RETURN` | `RAW_STOCK` | `RETURNED` |
| `DIRECT_SALE` | `RAW_STOCK` (raw silk and vuda warp only) | `CUSTOMER` |
| `CONSUMPTION` | `RAW_STOCK` | `INTERNAL_WIP` |
| `PRODUCTION_OUTPUT` | `INTERNAL_WIP` | `FINISHED_STOCK` |
| `WASTAGE` | `RAW_STOCK`, `INTERNAL_WIP`, `EXTERNAL_WIP` | `WASTAGE` |
| `OUTSOURCE_ISSUE` | `RAW_STOCK` | `EXTERNAL_WIP` |
| `OUTSOURCE_RECEIPT` | `EXTERNAL_WIP` | `FINISHED_STOCK` |
| `DELIVERY` | `FINISHED_STOCK` | `CUSTOMER` |
| `CUSTOMER_RETURN` | `CUSTOMER` | `FINISHED_STOCK` (silk/kora warp) or `RAW_STOCK` (raw silk/vuda warp) |
| `ADJUSTMENT` | any non-NULL location | any different location |

- `ck_material_movements_product_conversion CHECK (to_product_type = product_type OR (movement_type IN ('CONSUMPTION','OUTSOURCE_ISSUE') AND product_type = 'RAW_SILK' AND to_product_type IN ('SILK_WARP','KORA_WARP')))`
- `ck_material_movements_direct_sale CHECK (movement_type <> 'DIRECT_SALE' OR product_type IN ('RAW_SILK','VUDA_WARP'))` - finished warp leaves through `DELIVERY`
- `ck_material_movements_vuda CHECK (movement_type NOT IN ('CONSUMPTION','OUTSOURCE_ISSUE','OUTSOURCE_RECEIPT','PRODUCTION_OUTPUT') OR (product_type <> 'VUDA_WARP' AND to_product_type <> 'VUDA_WARP'))` - vuda warp is trade-only
- `ck_material_movements_location_products` - an internal location only ever holds its allowed products: on the source side use `product_type`, on the destination side `to_product_type`, with the same table as `ck_inventory_balances_location_product` (`RAW_STOCK`: RAW_SILK, VUDA_WARP; `INTERNAL_WIP`/`EXTERNAL_WIP`/`FINISHED_STOCK`: SILK_WARP, KORA_WARP). `SUPPLIER` as a source holds only RAW_SILK or VUDA_WARP
- `ck_material_movements_reference CHECK ((reference_type IS NULL) = (reference_id IS NULL) AND (movement_type IN ('OPENING_BALANCE','ADJUSTMENT') OR reference_id IS NOT NULL))`
- `ck_material_movements_reference_type CHECK (reference_type IS NULL OR reference_type IN ('PURCHASE','MATERIAL_RECEIPT','SUPPLIER_RETURN','ORDER_ITEM','PRODUCTION_BATCH','OUTSOURCING_JOB'))`
- `ck_material_movements_reason CHECK (movement_type <> 'ADJUSTMENT' OR (reason IS NOT NULL AND length(trim(reason)) > 0))`

Indexes: `ix_material_movements_product_date (product_type, movement_date)`, `ix_material_movements_to_product (to_product_type, to_location)`,
`ix_material_movements_from (product_type, from_location)`, `ix_material_movements_reference (reference_type, reference_id)`,
`ix_material_movements_type (movement_type)`, `ix_material_movements_created_by (created_by)`.

Which operation writes which movement and `reference_type`:

| Operation | movement_type | reference_type -> reference_id |
|---|---|---|
| Receive material (accepted kg only) | `RECEIPT` | `MATERIAL_RECEIPT` -> receipt id |
| Return to supplier | `PURCHASE_RETURN` | `SUPPLIER_RETURN` -> return id |
| Deliver raw silk / vuda | `DIRECT_SALE` | `ORDER_ITEM` -> item id |
| Deliver finished warp | `DELIVERY` | `ORDER_ITEM` -> item id |
| Customer return | `CUSTOMER_RETURN` | `ORDER_ITEM` -> item id |
| Start production | `CONSUMPTION` (input kg) | `PRODUCTION_BATCH` -> batch id |
| Complete production | `PRODUCTION_OUTPUT` (output kg); `WASTAGE` (wastage kg, reason `PRODUCTION_WASTAGE`); `WASTAGE` (discrepancy kg, reason `PRODUCTION_DISCREPANCY`) | `PRODUCTION_BATCH` |
| Issue to manufacturer | `OUTSOURCE_ISSUE` | `OUTSOURCING_JOB` |
| Receive from manufacturer | `OUTSOURCE_RECEIPT` (received kg); `WASTAGE` (difference kg, reason `OUTSOURCING_LOSS`) | `OUTSOURCING_JOB` |
| Opening stock at go-live | `OPENING_BALANCE` | none |
| Manual correction (owner) | `ADJUSTMENT` + `reason` | none |

## 13. Derived values (never stored)

All are SQL aggregations (GROUP BY / DTO projections), never per-row loops. "Active payment" means `payments.status = 'RECORDED'`:
an allocation of a `REVERSED` payment no longer counts, which is how a reversal "releases" allocations without editing them.

| Value | Exact logic |
|---|---|
| **Stock(product, location)** | Σ `quantity_kg` of movements where (`to_product_type`, `to_location`) matches, minus Σ where (`product_type`, `from_location`) matches. `inventory_balances.quantity_kg` is its cached copy (same transaction) and can be rebuilt with this query. |
| **Account balance** | Per `financial_account_id`: Σ `amount` where `direction = 'IN'` minus Σ where `direction = 'OUT'`, over all rows (reversal rows included). |
| **Total available money** | Σ of all account balances (cash + bank). |
| **Supplier payable per purchase (Q1)** | `payable = (Σ accepted_weight_kg of its receipts − Σ returned_weight_kg of its returns) * rate_per_kg`; `outstanding = payable − Σ allocated_amount` from `supplier_payment_allocations` joined to active payments. Cancelled purchases count 0. The result can be negative after a return (a credit with the supplier); aggregates show it as a credit, it is not clamped. |
| **Supplier payable per supplier** | Σ outstanding over the supplier's purchases + Σ over `opening_obligations` with `purpose = 'SUPPLIER'` minus their allocations. |
| **Purchase payment status** | `UNPAID` (no allocation), `PARTIALLY_PAID`, `PAID` (outstanding = 0), `OVERDUE` (outstanding > 0 and `due_date` < today from the injected clock). |
| **Customer outstanding per item (Q2)** | For items with `order_items.status <> 'CANCELLED'` whose order has status `CONFIRMED`, `IN_PROGRESS`, `READY`, `DELIVERED` or `COMPLETED`: `amount − Σ allocated_amount` from `customer_payment_allocations` joined to active payments. `PLACED` and `CANCELLED` orders owe nothing. |
| **Customer outstanding per customer** | Σ item outstanding + Σ `opening_obligations` (`purpose = 'CUSTOMER'`) outstanding. Age = today − `order_date` (or `obligation_date`) of the oldest unpaid obligation. |
| **Customer advance** | Σ `amount` of the customer's active payments − Σ allocations of those payments (never negative). Advance is not revenue. |
| **Order payment status** | From its items' allocations: `UNPAID`, `PARTIALLY_PAID`, `PAID`. `OVERPAID` cannot occur because an allocation can never exceed the outstanding. |
| **Manufacturer payable** | Per job (status <> `CANCELLED`): `received_weight_kg * rate_per_kg − Σ allocations` (`manufacturer_payment_allocations`, active payments); plus opening obligations (`purpose = 'MANUFACTURER'`). |
| **Worker payable** | Σ `amount` of the worker's `RECORDED` work records − Σ `worker_payment_allocations` (active payments); plus opening obligations (`purpose = 'WORKER'`). Per-record status: `UNPAID` / `PARTIALLY_PAID` / `PAID`. |
| **Loan outstanding principal** | `principal_amount − repaid_before_go_live − (Σ OUT amount of type LOAN_PRINCIPAL_REPAYMENT for the loan − Σ amount of REVERSAL rows whose original is one of those)`. |
| **Chit paid / received** | `prior_contributions_amount` + Σ `CHIT_CONTRIBUTION` (net of reversals) / Σ `CHIT_PAYOUT` (net of reversals) for the chit; organiser payments (`CHIT_ORGANISER_PAYMENT`) are shown separately. |
| **External WIP** | Total: balance of `EXTERNAL_WIP`. Per job: `issued_weight_kg − received_weight_kg − wastage_weight_kg` for jobs `MATERIAL_ISSUED` or `PARTIALLY_RECEIVED`; grouped by manufacturer for the dashboard. |
| **Production yield** | `output_weight_kg / input_weight_kg` for `COMPLETED` batches. Outsourcing recovery = `received / issued`. |
| **Operating expenses** | Σ `amount` of `RECORDED` expenses with `expense_kind = 'BUSINESS'` grouped by month/category. `PERSONAL` expenses are drawings and excluded from profit. |
| **Pending raw-silk shortfall** | Raw stock − Σ `required_weight_kg` of open order items needing production (dashboard insight). |

Revenue is never "all inflows": loans, transfers, chit payouts and advances are not sales revenue.

## 14. Ledger and immutability rules

| Table | Rule | Enforcement |
|---|---|---|
| `material_movements`, `financial_transactions`, `audit_log` | Insert only. Corrections are new rows (`ADJUSTMENT`, `REVERSAL`) | trigger `trg_<table>_immutable` + application (no update/delete code) |
| `material_receipts`, `supplier_returns`, `account_transfers`, `opening_obligations` | Insert only | trigger |
| the four `*_payment_allocations` | Insert only; a reversed payment's allocations stay and are ignored by queries | trigger |
| `payments`, `expenses`, `work_records` | Only the reversal columns (`status`, `reversed_at`, `reversal_reason`) change, once | application + `ck_*_reversal`; no trigger |
| `inventory_balances` | Updated only by `InventoryService` in the same transaction as the movement | application; `ck_*_quantity >= 0` |
| `purchases`, `customer_orders`, `order_items`, `production_batches`, `outsourcing_jobs`, `loans`, `chits` | Status moves only along legal transitions via entity methods (section 15) | application + `ck_*_status` |

**Trigger (migration V15, simple and justified):** one function `prevent_row_modification()` that raises an exception on `UPDATE` or `DELETE`,
attached `BEFORE UPDATE OR DELETE ... FOR EACH ROW` to the insert-only tables above. It is the last line of defence for rule 5 (history is immutable).
Because a row trigger does not fire on `TRUNCATE`, tests clean data with `TRUNCATE ... CASCADE`, never `DELETE`.

**Locking anchors (ADR-010):**

| Operation | Lock |
|---|---|
| Any stock movement | `PESSIMISTIC_WRITE` on the affected `inventory_balances` rows, in a fixed order (by product, then location) |
| Receipt / return on a purchase | `PESSIMISTIC_WRITE` on the `purchases` row |
| Cash/bank out, transfer | `PESSIMISTIC_WRITE` on the `financial_accounts` row(s), ascending `id` order |
| Payment recording (allocation) | `PESSIMISTIC_WRITE` on the payer/payee `parties` row, so two payments of one party never allocate the same outstanding twice |
| Business number | `PESSIMISTIC_WRITE` on the `business_number_sequences` row |
| Editable aggregates (orders, purchases, jobs, batches, master data) | optimistic `@Version` -> `CONCURRENT_MODIFICATION` |

## 15. Status columns and legal transitions

Transitions happen only through named entity methods; anything else is `INVALID_STATE_TRANSITION` (409).

| Table.column | Allowed values | Legal transitions |
|---|---|---|
| `parties.status` | `ACTIVE`, `INACTIVE` | `ACTIVE` <-> `INACTIVE` |
| `financial_accounts.status` | `ACTIVE`, `CLOSED` | `ACTIVE` -> `CLOSED` |
| `purchases.status` | `ORDERED`, `PARTIALLY_RECEIVED`, `FULLY_RECEIVED`, `CANCELLED` | `ORDERED` -> `PARTIALLY_RECEIVED` -> `FULLY_RECEIVED`; `ORDERED` -> `FULLY_RECEIVED` (one receipt for everything); `ORDERED` -> `CANCELLED` (only when nothing was received) |
| `customer_orders.status` | `PLACED`, `CONFIRMED`, `IN_PROGRESS`, `READY`, `DELIVERED`, `COMPLETED`, `CANCELLED` | `PLACED` -> `CONFIRMED` -> `IN_PROGRESS` -> `READY` -> `DELIVERED` -> `COMPLETED`; `CONFIRMED` -> `READY` (filled from existing stock, no production); `COMPLETED` is set explicitly after `DELIVERED`; `PLACED`/`CONFIRMED` -> `CANCELLED` (not when allocations exist: reverse the payment first). Locked (`ORDER_LOCKED`) from `IN_PROGRESS` |
| `order_items.status` | `PENDING`, `IN_PROGRESS`, `READY`, `DELIVERED`, `CANCELLED` | `PENDING` -> `IN_PROGRESS` -> `READY` -> `DELIVERED`; `PENDING` -> `CANCELLED` (with the order). An item is delivered whole (no partial delivery) |

| `expenses.status` | `RECORDED`, `REVERSED` | `RECORDED` -> `REVERSED` |
| `work_records.status` | `RECORDED`, `REVERSED` | `RECORDED` -> `REVERSED` |
| `production_batches.status` | `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED` | `PLANNED` -> `IN_PROGRESS` -> `COMPLETED`; `PLANNED` -> `CANCELLED` |
| `outsourcing_jobs.status` | `CREATED`, `MATERIAL_ISSUED`, `PARTIALLY_RECEIVED`, `COMPLETED`, `CANCELLED` | `CREATED` -> `MATERIAL_ISSUED` -> `PARTIALLY_RECEIVED` -> `COMPLETED`; `MATERIAL_ISSUED` -> `COMPLETED` (single receipt); `CREATED` -> `CANCELLED` |

## 18. Decisions made while writing

Where the sources were silent or disagreed, the simplest option consistent with the rules was taken:

1. **Raw silk becomes warp inside WIP.** A movement has `product_type` (leaving) and `to_product_type` (arriving). WIP locations hold the warp type being made. Without this, `INTERNAL_WIP`/`EXTERNAL_WIP` could not be decremented by `PRODUCTION_OUTPUT`/`OUTSOURCE_RECEIPT`. The service signature gains an optional destination product (defaulting to the source product).
2. **Vuda warp is purchased** (baseline requirement 6.3), so `purchases.product_type` exists (`RAW_SILK` or `VUDA_WARP`). Vuda warp is trading stock and lives in `RAW_STOCK`: a vuda `RECEIPT` goes `SUPPLIER` -> `RAW_STOCK`, `PURCHASE_RETURN` and `DIRECT_SALE` leave `RAW_STOCK`. This matches DOMAIN_RULES section 3 without a rule change. A customer return of raw silk or vuda goes back to `RAW_STOCK`. `FINISHED_STOCK` holds only silk and kora warp.
3. **Production discrepancy and outsourcing loss** leave WIP as `WASTAGE` movements with a `reason` (`PRODUCTION_DISCREPANCY`, `OUTSOURCING_LOSS`). No new movement type.
4. **`ADJUSTMENT` cannot make an internal balance negative** (ADR-026): `ck_inventory_balances_quantity >= 0` is kept (roadmap task 2.1). An adjustment needs the `INVENTORY_ADJUST` permission and a mandatory `reason`; it may add or remove stock against an external location (`SUPPLIER`, `CUSTOMER`, `WASTAGE`, `RETURNED`) without a business document.
5. **No `locked` column on orders** and no stored payment/paid statuses (DOMAIN_RULES rules: derived values are never stored; `canModify()` derives the lock).
6. **No `total_amount` on purchases.** Totals are derived; `due_date` is stored (historical) and checked against `purchase_date + credit_days`.
7. **Loans link to a party** (`loans.party_id`, as in the exact-schema design) whose role is `LENDER`, a fifth party role added to V3's CHECK. `loan_type` (`BANK`/`PRIVATE`) is kept. Lenders get phones and contact details like any party.
8. **No pending-cheque state, no refunds.** Every ledger row counts immediately; corrections are `REVERSAL` rows. `REFUND` is out of the MVP. A manual cash/bank correction is the `ADJUSTMENT` transaction type (FR-FIN-15): `FINANCE_MANAGE`, a reason in `description`, never makes the account negative, audited `ACCOUNT_ADJUSTED`. `CHIT_ORGANISER_PAYMENT` (OUT, `chit_id`) records payments to the chit organiser (FR-CHIT-04).
9. **Account types are `CASH` and `BANK` only** (DOMAIN_RULES); the design note's `UPI` is a payment method, not an account type.
10. **`work_records` and `expenses` have status `RECORDED`/`REVERSED`**: a reversal sets the status and writes the compensating financial transaction (or releases the payable), so a mistaken entry is corrected without deleting history. Work-record paid status stays derived.
11. **Outsourcing receipts** have no table of their own: running totals live on the job and each receipt writes movements. Part of the history is therefore in `material_movements` (`reference_type = 'OUTSOURCING_JOB'`).
12. **Opening obligations** (`opening_obligations`) carry a `purpose` and are valid allocation targets in all four allocation tables, so go-live balances are settled by the same oldest-first engine.
13. **Reminder timing** is `days_before_due` (default 3, configurable 0-30), a reminder on the due date, then every `overdue_repeat_days` (default 1) while overdue. No penalty amount (Q3).
14. **Immutability triggers** are added only to insert-only tables (one tiny function). Business-rule triggers are not used.
15. **Junction tables** (`production_order_items`, `outsourcing_order_items`) have composite PKs and only `created_at`/`created_by`; they carry no `version`.
16. **Transcript conflicts resolved:** the design notes use `WAREHOUSE`/`MAIN_STOCK` for raw stock (the rules say `RAW_STOCK`); `CREATED` as the first order status (the rules say `PLACED`); `COMPLETED` for payments (the rules say `RECORDED`); `payments.direction` values `RECEIVED`/`PAID` kept; `ON DELETE CASCADE` on junctions rejected (nothing is deleted).
17. **`audit_log` is created in V10** (Phase 3, with the first reversals) and carries `request_id`; its action list is the `AuditAction` enum shared with `09-SECURITY.md`. Login lockouts are audited from Phase 3 on (earlier only a WARN log line).
18. **Go-live loans and chits:** a loan running before go-live is registered with `POST /loans/existing`: `principal_amount` is the original principal and `repaid_before_go_live = principal_amount − outstanding principal`, with no `LOAN_RECEIVED` transaction (that money is already inside the account opening balances); a chit running before go-live records `prior_contributions_count` and `prior_contributions_amount`, with no cash transaction. Loans also carry `interest_notes` (max 500).
