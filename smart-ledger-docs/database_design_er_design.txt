Step 7.1 — Detailed ER Design

Now we move from “what tables do we need?” to “exactly how do these tables connect?”

This is an important stage because a weak ER design will create problems later in JPA, transactions, reporting, and inventory calculations.

Our target is:

Production-grade relational design, but still realistic for a 1-month SmartSilk MVP.

7.1.1 First: Decide the Party Model

We have four kinds of people/businesses:

Customer
Supplier
Manufacturer
Worker

A payment can involve any of them.

A naïve design would create:

payments
 ├── customer_id
 ├── supplier_id
 ├── manufacturer_id
 └── worker_id

This creates awkward nullable columns.

For example:

payment_id = P001
customer_id = C001
supplier_id = NULL
manufacturer_id = NULL
worker_id = NULL

And we'd need a CHECK constraint saying exactly one must be populated.

Better design

Create a common parties table.

                    ┌──────────────┐
                    │    parties   │
                    ├──────────────┤
                    │ id           │
                    │ name         │
                    │ phone        │
                    │ address      │
                    │ status       │
                    └──────┬───────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
     customers         suppliers       manufacturers
          │
       workers

However, we don't actually need four separate subtype tables if they contain almost no additional information.

For SmartSilk MVP, I recommend:

parties
Field	Purpose
id	UUID PK
party_code	CUST-001 / SUP-001 etc.
name	Person/business name
phone	Contact
address	Address
party_type	CUSTOMER / SUPPLIER / MANUFACTURER / WORKER
status	ACTIVE / INACTIVE
created_at	Audit
updated_at	Audit

If a person can have multiple roles, make party_type a role relationship instead of a single enum later.

For the MVP, a single role is sufficient unless your father's actual workflow requires the same party to be both customer and supplier.

Why this is useful

Now:

Payment
   ↓
Party

instead of:

Payment
   ↓
Customer OR Supplier OR Manufacturer OR Worker

This makes finance much cleaner.

7.1.4 Material Movement — One of the Most Important Tables

Do not simply store:

raw_silk_stock = 1200 kg

because then you don't know why it became 1100 kg.

Instead:

Material Movement

is the inventory ledger.

material_movements
Field	Meaning
id	PK
movement_number	INV-MOV-001
product_type	RAW_SILK / KORA_WARP / SILK_WARP / VUDA_WARP
quantity_kg	Quantity
movement_type	RECEIPT / CONSUMPTION / SALE / RETURN / TRANSFER / PRODUCTION_OUTPUT / OUTSOURCE_ISSUE / OUTSOURCE_RECEIPT / WASTAGE
from_location	Source
to_location	Destination
movement_date	Date
reference_type	Optional business reference
reference_id	Optional reference ID
notes	Explanation
audit fields	timestamps

Think of it as:

                    MATERIAL MOVEMENTS
                           │
       ┌───────────────────┼──────────────────┐
       │                   │                  │
     Receipt            Consumption         Output
       │                   │                  │
       ▼                   ▼                  ▼
   +300 kg             -100 kg              +90 kg

The current stock is derived from these movements.

7.1.7 Production

Production is related to order items, but we should not force:

One order = one production batch

because that's not always true.

Example:

Order Item
100 kg

       ↓
Batch 1 → 40 kg
Batch 2 → 60 kg

Or:

Batch 1
   ↓
Order Item A → 50 kg
Order Item B → 40 kg

Therefore:

ProductionBatch N ───── M OrderItem

with a junction table.

production_batches
Field	Meaning
id	PK
batch_number	PB-001
production_date	Date
product_type	Warp type
input_weight_kg	Silk consumed
output_weight_kg	Warp produced
wastage_weight_kg	Wastage
status	STARTED / COMPLETED / CANCELLED
notes	Notes
production_order_items
Field	Meaning
production_batch_id	FK
order_item_id	FK
allocated_weight_kg	Portion fulfilled

Composite primary key:

(production_batch_id, order_item_id)

This gives:

Production Batch
       │
       ├──── Order Item A
       │
       └──── Order Item B

7.1.9 Workforce

Worker payments and worker work must remain separate.

work_records
Field	Meaning
id	PK
worker_id	FK → parties
work_date	Date
work_type	ROLLING / WARPING
quantity_kg	For kg-based work

Important:

Never calculate historical worker payment using today's rate.

If the worker was paid ₹X/kg at the time, the record stores ₹X/kg.

7.1.11 Payment Allocation

This is critical.

Suppose customer owes:

Order A = ₹30,000
Order B = ₹20,000
Order C = ₹40,000

Customer pays:

₹50,000

One payment must be allocated:

PAY001 ₹50,000
       │
       ├── Order A → ₹30,000
       └── Order B → ₹20,000

Therefore:

Payment 1 ───── N PaymentAllocation

For production-grade relational integrity, I recommend specific allocation tables rather than one generic reference_type/reference_id.

For example:

customer_payment_allocations
Field	Meaning
id	PK
payment_id	FK → payments
order_id / order_item_id	FK
allocated_amount	Amount

Similarly:

supplier_payment_allocations
manufacturer_payment_allocations
worker_payment_allocations

This is slightly more tables, but gives us actual foreign-key integrity.

For a 1-month MVP, we can initially implement customer/supplier/manufacturer allocation and add worker allocation if needed.

7.1.14 Internal Transfers

Suppose:

Bank → Cash
₹20,000

This is not income.

We need two financial movements:

Bank
 -₹20,000

Cash
 +₹20,000

A clean design is:

account_transfer
       │
       ├── source transaction
       └── destination transaction
account_transfers
Field	Meaning
id	PK
transfer_number	TRF-001
source_account_id	FK
destination_account_id	FK
amount	Amount
transfer_date	Date
notes	Notes

Then the two corresponding financial transactions can point to the transfer.

This prevents SmartSilk from incorrectly treating transfers as revenue/expense.

7.1.16 Loans

A loan is not an expense when principal is received.

Example:

Borrow ₹1,00,000

means:

Cash +₹1,00,000
Loan Liability +₹1,00,000

Later:

Repay principal ₹20,000
Interest ₹3,000

means:

Loan principal → liability decreases
Interest → expense
loans
Field	Meaning
id	PK
loan_number	LOAN-001
party_id	Lender
principal_amount	Principal
start_date	Start
status	ACTIVE / CLOSED
notes	Notes

Loan-related money movements are recorded in finance.

7.1.20 Delete Rules

This is very important.

For financial and inventory records:

Do NOT allow normal deletion.

For example:

Purchase
Payment
Expense
Material Movement
Financial Transaction
Production Batch

should generally be:

ACTIVE
REVERSED
CANCELLED

rather than physically deleted.

Example

Wrong:

DELETE payment PAY001

Better:

PAY001
status = REVERSED

and create the appropriate reversal transaction.

This preserves the audit trail.

7.1.21 Foreign-Key Delete Policy

Recommended:

Master data

Customer/Supplier/Worker:

ON DELETE RESTRICT

if referenced by business records.

Instead:

status = INACTIVE
Transaction data
ON DELETE RESTRICT

Almost everywhere.

Junction tables

For example:

production_order_items

can use:

ON DELETE CASCADE

because the junction has no independent meaning without its parent.

7.1.23 Important Check Constraints

Examples:

weight > 0
amount > 0
rate >= 0
credit_days >= 0
quantity >= 0

For production:

output + wastage <= input

or, depending on your discrepancy policy:

input = output + wastage + discrepancy

Some cross-table business rules cannot be enforced with a simple PostgreSQL CHECK constraint. Those belong in the application/domain layer.

7.1.25 The Most Important Architectural Decision

Notice something important:

We now have three different ledgers.

1. Inventory ledger
material_movements

Answers:

Where did the silk/warp go?

2. Business settlement ledger
payments
payment_allocations

Answers:

Who owes whom, and which obligation did the payment settle?

3. Money ledger
financial_transactions

Answers:

Where did the actual money move?

This separation is extremely valuable.

For example:

Customer pays ₹50,000 through bank for Order #101

Order
   ↓
Payment
   ↓
Payment Allocation
   ↓
Financial Transaction
   ↓
Bank Account

One business event, but different representations for different purposes.

What you should understand before moving on

You should now be able to answer these in an interview:

Why isn't stock stored directly in purchases?

Because inventory is the result of material movements, not merely purchasing.

Why are Payment and FinancialTransaction separate?

Because payment represents business settlement while the financial transaction represents actual money movement.

Why do we need PaymentAllocation?

Because one payment can settle multiple obligations and one obligation can be settled by multiple payments.

Why is ProductionBatch ↔ OrderItem many-to-many?

Because one batch can fulfill multiple order items and one order item can be fulfilled by multiple batches.

Why don't we delete financial records?

Because financial and inventory records require auditability and reversals.

Why do we need AccountTransfer?

Because moving ₹20,000 from Bank A to Cash is neither revenue nor expense; it moves value between accounts.
