Step 7 — Database Design

Now we convert the domain model into an actual PostgreSQL database design.

The important distinction is:

Domain model tells us what the business means. Database design tells us how we persist that meaning safely.

We should design the database before creating JPA entities, otherwise it is easy to let Java classes accidentally dictate the business model.

7.1 Database Design Goals

SmartSilk's database must guarantee:

Financial records are not accidentally lost.
Inventory cannot silently become inconsistent.
Historical prices and rates remain unchanged.
Payments can be allocated correctly.
Partial purchases and returns are supported.
Production and outsourcing can be traced.
Cash and each bank account remain separate.
Important relationships are enforced by foreign keys.
Invalid states are prevented as much as possible by database constraints.
The schema remains understandable enough for you to maintain.
7.2 PostgreSQL as the Source of Truth

For the MVP:

Kotlin
   ↓
Spring Boot
   ↓
PostgreSQL

PostgreSQL is the authoritative persistent store.

Do not keep important business data only in:

frontend state
Redis
memory
generated reports
AI context
dashboard caches

Those can be temporary representations.

7.3 Database Organization

We don't need separate databases for every module.

One database is enough:

smartsilk

Conceptually:

smartsilk
│
├── identity
├── parties
├── procurement
├── inventory
├── orders
├── production
├── outsourcing
├── workforce
├── finance
├── loans
├── chits
├── documents
└── notifications

Whether these become PostgreSQL schemas or simply table naming/package boundaries can be decided during implementation.

For your one-month project, one PostgreSQL schema with clear table names is simpler.

7.4 ID Strategy

Every major entity needs a stable primary key.

For example:

customer.id
supplier.id
purchase.id
customer_order.id
payment.id

I recommend using:

UUID identifiers

rather than exposing sequential business IDs as the primary key.

Why?

Because:

1
2
3
4

is predictable.

UUIDs are better suited to APIs and future distributed systems.

However, users should still see human-friendly references such as:

PUR-2026-0012
ORD-2026-0048
PAY-2026-0071

So we separate:

Internal ID
+
Business Reference Number

7.6 Soft Delete vs Hard Delete

This is especially important for financial data.

Do not physically delete:

payments
financial transactions
purchases
material movements
expenses
loans
chit transactions

Instead, use status/correction/reversal mechanisms.

For master data such as a customer:

ACTIVE
INACTIVE

is generally better than deleting the customer.

7.10 Why Receipt and Purchase Must Be Separate

Consider:

Purchase = 180 kg
Received = 100 kg

If we store only one purchase quantity, we lose the distinction between:

“We ordered 180 kg”

This distinction matters for:

supplier follow-up

7.12 Why Material Movement Is Central

Suppose SmartSilk has:

+180 kg received
-30 kg direct sale
-50 kg production
-40 kg outsourcing
-5 kg wastage

Then:

Available raw silk
= 180 - 30 - 50 - 40 - 5
= 55 kg

The system can derive this from movements.

We don't need an independently editable:

raw_silk_available = 55

because that can become inconsistent.

I recommend storing readable strings rather than database-specific enum types for the MVP.

That makes migrations easier.

7.18 Production and Inventory

A production operation should generate material movements.

For example:

Production starts
      ↓
PRODUCTION_CONSUMPTION
      ↓
Internal WIP

Then:

Production completes
      ↓
PRODUCTION_OUTPUT
      ↓
Finished Stock

The production table describes the business operation.

The material movement table records the physical inventory effect.

That separation is important.

7.33 Important Database Constraints

The database should enforce basic impossible states.

Examples:

Weight
weight > 0
Money
amount >= 0
Rates
rate >= 0
Production
output + wastage + discrepancy
≤/=
input

The exact enforcement may partly live in application/domain logic because cross-row business rules are difficult to enforce purely with simple SQL constraints.

7.34 Unique Constraints

Examples:

customer business reference
supplier business reference
invoice number

Potentially:

phone

but only if the business guarantees phone numbers are unique.

Do not blindly put unique constraints on every seemingly identifying field.

7.35 Indexing Strategy

Indexes should support actual query patterns.

Likely indexes:

customers(name)
suppliers(name)

purchases(supplier_id)
purchases(purchase_date)

material_receipts(purchase_id)

material_movements(product_type, movement_date)

customer_orders(customer_id)
customer_orders(status)

order_items(order_id)

payments(payment_date)

payment_allocations(payment_id)

financial_transactions(account_id, transaction_date)

outsourcing_jobs(manufacturer_id, status)

work_records(worker_id, work_date)

Don't create indexes everywhere.

Indexes improve reads but increase write/storage cost.

7.36 Money Storage

Never store money as floating-point numbers.

Avoid:

FLOAT
DOUBLE

Use a precise decimal representation.

Conceptually:

DECIMAL / NUMERIC

For example:

₹1250.50

must not become:

1249.999999

Financial precision is non-negotiable.

7.37 Weight Storage

Weight is also important.

Use a fixed-precision decimal representation.

For example:

100.250 kg

should be representable exactly enough for the business.

Don't use floating point for inventory quantities if precision matters.

7.38 Dates and Times

Use appropriate timestamp/date types.

For example:

Business date → DATE
Actual transaction timestamp → timestamp with timezone where appropriate

A purchase may care about:

purchase_date

while an actual financial transaction may need:

transaction_timestamp

Do not automatically store everything as timestamps.

7.39 Auditability

For financial and inventory records, the system should eventually answer:

Who created this?

When was it created?

Was it corrected?

What was the original value?

This is why we avoid destructive updates/deletes.

For example, if a payment was wrong:

Bad:

UPDATE payment
SET amount = 50000

without history.

Better:

Original payment
       ↓
Correction / reversal
       ↓
Corrected transaction

The exact correction mechanism will be designed during backend implementation.

7.40 Database Migration Strategy

We should use:

Flyway

Database changes should be version-controlled.

Conceptually:

V1__create_party_tables.sql
V2__create_procurement_tables.sql
V3__create_inventory_tables.sql
V4__create_order_tables.sql
V5__create_production_tables.sql
...

This means your database schema becomes part of the project source code.

Do not manually create production tables through random SQL commands and forget how you created them.

That looks flexible but becomes difficult to validate and understand.

Instead, maintain meaningful domain tables:

Loan

Material Movement
Production Batch
Outsourcing Job

Then connect them.

This is much easier to reason about.

7.43 Database Design Principles to Freeze

For SmartSilk:

Principle 1

Financial data uses exact numeric types.

Principle 2

Inventory is movement-based.

Principle 3

Business operations and financial transactions remain separate.

Principle 4

Historical prices/rates are immutable after recording unless explicitly corrected.

Principle 5

Important financial/inventory records are not hard-deleted.

Principle 6

Foreign keys protect relationships.

Principle 7

Database constraints prevent simple invalid states.

Principle 8

Business invariants are enforced in the application/domain layer.

Principle 9

All schema changes use Flyway migrations.

Principle 10

The frontend never directly accesses PostgreSQL.
